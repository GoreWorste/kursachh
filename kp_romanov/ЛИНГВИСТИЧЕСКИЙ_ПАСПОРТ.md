# Лингвистический паспорт пояснительной записки (курсовой проект)

**Источник образца:** `Пример_ПЗ.txt` — пояснительная записка курсового проекта «Интернет-магазин бытовой техники» (тема задания в том же файле: веб- и мобильные приложения продажи туристических товаров).  
**Назначение документа:** единый стиль для написания ПЗ по проекту **Skynet** (курсовая работа Романова), без «нейросетевой» гладкости и с опорой на реальные формулировки образца.

---

## 1. Общий профиль стиля

| Параметр | Норма |
|----------|--------|
| Регистр | Официально-деловой, учебный (техникум, 3 курс) |
| Лицо | Без «мы»; безличные и пассивные конструкции («было разработано», «использовалось», «предусмотрено») |
| Объём предложения | В среднем **20–35 слов**; допустимы длинные перечисления через запятую |
| Лексика ИТ | **WEB-ресурс**, **веб-сервис**, **информационная система**, **реляционная база данных**, **СУБД**, **API**, **клиент-серверный** — как в образце (латиница WEB заглавными) |
| Ошибки образца | Допустимы лёгкие огрехи уровня студента (согласование, опечатки) — **не** выравнивать текст до идеала ИИ |

Стиль: **чуть тяжёлый, перегруженный оборотами**, но узнаваемый как студенческий техникумский, а не как сгенерированная статья.

---

## 2. Топ-20 вводных слов и клише (из образца)

Частотные и характерные связки (подсчёт и выборка по `Пример_ПЗ.txt`):

| № | Клише / связка | Контекст употребления |
|---|----------------|------------------------|
| 1 | **На сегодняшний день** | Начало ВВЕДЕНИЯ |
| 2 | **В связи с этим** | Связка после тезиса о развитии отрасли/Интернета |
| 3 | **В данной курсовой работе** / **курсового проекта** | Постановка цели разработки |

| 9 | **представлен / представлена / представлено** | Подписи и текст к рисункам (**~129** вхождений «представлен» в файле) |
| 10 | **показан / показано** | «На рисунке 31 показан пример…» |
| 11 | **изображена / изображены** | «На рисунке 18 изображена работа паттерна…» |
| 12 | **В качестве** | Средства разработки, СУБД, сервер (**~7** раз) |
| 13 | **В результате** | Итог разработки (**~2** в Заключении, допустимо чаще) |
| 14 | **В процессе** | «В процессе разработки…», «В процессе анализа…» |
| 15 | **было разработано / был разработан** | Итог КП |
| 16 | **было выполнено / была проведена** | Тестирование, анализ |
| 17 | **на основе проведённого анализа** | Перед проектированием БД |
| 18 | **На этапе** | «На этапе анализа», «На этапе проектирования», «На этапе тестирования» |

«Данное программное решение», «разработанное решение», «программное изделие», «функциональные возможности», «в соответствии с требованиями», «под управлением СУБД», «осуществляется», «необходимо» (**~49** вхождений), «с целью», «с помощью», «благодаря», «одной из», «в основном».

**Редко в образце (не навязывать):** «Таким образом», «необходимо отметить», «представляется целесообразным», «исходя из анализа», «в рамках данного проекта», «вследствие вышеизложенного» — при необходимости **1–2 раза** на всю ПЗ, не чаще.

## 3. Синтаксис

### 3.1. Пассив и безличность (доминируют)

- **Было / были:** «было разработано», «были выявлены», «были заданы атрибуты», «были определены роли».
- **Представляет собой:** «которое является WEB-ресурсом…», «интернет-магазин – это система, позволяющая…».
- **Предназначена / предназначен:** «Программа предназначена для использования…», «Веб-сервис предназначен для осуществления продажи…».
- **Используется / использовалось / использовался:** «использовалось ПО», «использовался фреймворк», «используется защита».
- **Осуществляется / осуществлял:** «осуществляется обновление модели», «клиент осуществляет запрос», «осуществлять учёт», «осуществлять предварительный заказ».

### 3.2. Деепричастные и причастные обороты

Длинные предложения с причастиями — норма:

> «Разработанный интернет-магазин позволит клиентам осуществлять предварительный заказ… без необходимости поиска товара на полках магазина.»

> «Перед разработкой на основе проведённого анализа при помощи построенных диаграмм IDEF0… была построена логическая схема данных.»

### 3.3. Перечисления

- В скобках длинные списки сущностей БД: «информация о пользователе, наименование роли, …».
- Через «а также», «в том числе», «и т.п.», «и т.д.» в конце перечня процессов.

### 3.4. Запрещённые синтаксические приёмы для «чистого ИИ»

- Избегать риторических вопросов.
- Не строить каждый абзац по схеме «тезис — аргумент — вывод» с идеальной симметрией.
- Не злоупотребляать тире и двоеточиями в каждом втором предложении.

## 4. Тон и местоимения

| Делать | Не делать |
|--------|-----------|
| «необходимо разработать», «требуется» | «мы разработали», «наш проект» |
| «было выполнено тестирование» | «я протестировал» (кроме редких цитат из отчёта) |
| «разработан веб-сервис» | «я создал отличный сервис» |
| «видно, что сценарий работает» | Рекламные оценки («лучший», «идеальный») |
| «удобный», «простой» — умеренно | «революционный», «уникальный опыт» |

**Заключение** — перечень этапов в прошедшем времени: анализ → проектирование → разработка → тестирование → соответствие задачам → перспективы для организации.

## 5. Подписи к рисункам

### 5.1. Как в образце

- В тексте: **«На рисунке 22 представлена архитектурная схема…»**, **«Пример инкапсуляции представлен на рисунке 15»**, **«На рисунках 28–30 представлен результат…»**.
- Подпись под рисунком: **`Рисунок N. Краткое название`** (с **точкой** после номера):  
  `Рисунок 22. Архитектурная схема WEB-ресурса`  
  `Рисунок 15. Инкапсуляция`
- Вариант с заглавной: **«На Рисунке 25 представлен…»** — встречается; для новой ПЗ лучше единообразие: **«рисунке»** со строчной.
- Иногда номер «отрывается» от подписи в исходнике (артефакт вёрстки) — в новой работе **не повторять**.

### 5.2. Целевой формат (ГОСТ для Skynet)

**В тексте:** «На рисунке 3 представлена архитектурная схема…» (как в образце).  
**Подпись:** **`Рисунок 3 – Архитектурная схема клиент-серверного WEB-ресурса`** — **тире (–)**, не точка; название с заглавной буквы; без точки в конце подписи (по ГОСТ 7.32–2017).

| Элемент | Образец | Цель Skynet |
|---------|---------|-------------|
| Разделитель | `Рисунок 15. Инкапсуляция` | `Рисунок 15 – Инкапсуляция` |
| В тексте | «на рисунке 15» | то же |
| Ссылка на приложение | «приведен в Приложении Д» | «приведена в приложении …» |

---

## 6. Подписи к таблицам

### 6.1. Как в образце

Единый формат с **точкой**:  
`Таблица 1. Программные средства разработки ПО`  
`Таблица 2. Технические характеристики ноутбука при разработке ПО`  
`Таблица 5. Клиентские возможности` (в приложении тестов)

В тексте: **«представлено в таблице 1»**, **«Характеристики представлены в таблице 2»**, **«приведены в таблице 1»**.

### 6.2. Целевой формат (ГОСТ)

**`Таблица 1 – Программные средства разработки`** (тире).  
Допустимо сохранить стиль образца с точкой, если вуз требует единства с прошлыми работами — **в одной ПЗ один стиль**.

---

## 7. Структура разделов

### 7.1. ВВЕДЕНИЕ

1. **«На сегодняшний день…»** — актуальность (Интернет, отрасль, автоматизация).  
2. **«В связи с этим…»** — следствие для бизнеса/пользователей.  
3. Определение предмета (**«… – это система, позволяющая…»**).  
4. **«В данной курсовой работе необходимо…»** — цель ПЗ.  
5. Кратко — что даст **разработанный** продукт (клиентам и организации).

### 7.2. Начало подразделов (1.1, 2.1, 2.2…)

- **Тематическое предложение** без вводного «В данном разделе»:  
  «Автоматизировать и упростить процесс учёта…» (цель).  
  «Разработать информационную систему (веб-сервис)…» (постановка).  
  «Разработать программное решение для перевода… в электронный вид.» (описание задачи).

### 7.3. Переходы между разделами

| Откуда → куда | Типичная связка |
|---------------|-----------------|
| Анализ → проектирование | «Перед разработкой … был проведён анализ…» |
| Роли → архитектура | «На основе спроектированной диаграммы прецедентов…» |
| Теория → практика | «При разработке Web-сервиса использовалась технология…» |
| Разработка → результат | «В результате выполнения поставленной задачи, было разработано…» |
| Основная часть → технологическая | «В качестве ядра базы данных было выбрано…» |
| Тесты | «Целью проведения испытаний является проверка соответствия…» |

### 7.4. ЗАКЛЮЧЕНИЕ

Цепочка: **«За время выполнения курсового проекта…»** → этапы (анализ, IDEF0, проектирование, настройка сервера, реализация, тестирование) → **«Результат … соответствуют поставленным задачам»** → достоинства интерфейса → область применения → маркетинговые выгоды списком «за счёт».

## 8. Шаблон описания ролей

**Точная формула образца:**

```text
Пользователь с ролью «<Наименование роли>» обладает следующими возможностями:
•	<Действие 1>;
•	<Действие 2>;
•	<Действие N>.
```

**Правила:**

- Кавычки **«ёлочки»** вокруг роли.
- Наследование ролей: **«Возможности покупателя;»** / **«Возможности неавторизированного пользователя;»** — первым пунктом.
- Пункты с маркером **•** (табуляция после буллета).
- **Точка с запятой** в конце каждого пункта, **кроме последнего** (в образце последний иногда без «;» — лучше **без точки с запятой на последнем**).
- Глаголы в форме отглагольных существительных: «Вывод списка…», «Изменение статуса…», «Управление корзиной».
- Допустимы **сбои форматирования** как в образце (пункт без «•», слитые строки) — в финальной ПЗ **выровнять**, но тон списка сохранить.

**Для функциональных требований (раздел 2.1.3)** — тот же буллет **•**, формулировки **«Возможность …»** / **«Отображение …»**.

## 9. Списки возможностей и требований

| Тип | Формат |
|-----|--------|
| Требования к веб-сервису | `•	Возможность авторизации и регистрации;` |
| Роли | `•	Поиск товаров;` |
| Заключение (выгоды) | `•	круглосуточного канала сбыта товаров;` (со строчной допустимо) |
| Вложенные группы (интерфейс) | `•	управления товарами («Список товаров», …),` |

**Не использовать** нумерованные списки для перечня функций клиента — только маркеры.

## 10. Терминология предметной области (Skynet)

Подставить вместо «интернет-магазин / бытовая техника»:

- **WEB-ресурс** «Skynet» / **веб-сервис** «Skynet»
- **информационная система**, **программное решение**, **программное изделие**
- **реляционная база данных**, **логическая / физическая модель данных**
- **клиент-серверная архитектура**, **WEB-API**, **паттерн MVC**
- **роли:** неавторизованный пользователь, покупатель, администратор и т.д. — по проекту
- **защитное программирование**, **блок try…catch**, **атрибуты валидации**

Сохранять **смешение** «сайт» / «веб-сайт» / «WEB-ресурс» как в образце — не синонимизировать насильно.

## 11. Слова и обороты, которых избегать («AI-штампы»)

В образце **отсутствуют** — не вводить в Skynet:

- «В современном мире…»
- «Играет ключевую роль…»
- «Революционный / инновационный / передовой подход»
- «Комплексное решение всех задач»
- «Данный инструмент позволяет значительно повысить эффективность» (без конкретики)
- «В заключение хотелось бы отметить»
- «Является неотъемлемой частью»
- «Мощный функционал», «интуитивно понятный интерфейс» (клише маркетинга)
- Обращения к читателю: «вы можете», «давайте рассмотрим»
- Английские вставки без нужды: «best practices», «cutting-edge»

**Допустимые «студенческие» шероховатости** (как в образце):  
«становиться» вместо «становится», «приставлена», «предсталвена», согласование «результат … соответствуют», «в процессе настройке» — **не копировать намеренно**, но и **не полировать** текст до журнального уровня.

## 12. Сравнение: образец vs целевой стиль Skynet

| Критерий | Образец (ПЗ магазин) | Skynet (цель) |
|----------|----------------------|---------------|
| Уровень | 3 курс, техникум | Тот же |
| Пассив | Доминирует | Сохранить |
| Длина фраз | Длинные, с перечислениями | 20–35 слов в среднем |
| Рисунки | «Рисунок N.» + «На рисунке N представлен…» | Подпись: **тире**; в тексте — как в образце |
| Таблицы | «Таблица N.» | Предпочтительно **тире** по ГОСТ |
| Идеальность | Опечатки, табуляции, пропуски «•» | Чуть аккуратнее вёрстки, **тон** — как у студента |
| ИИ | Нет «современного мира» | Не добавлять нейросетевые клише |

## 13. Мини-шаблоны абзацев (для копирования с подстановкой)

**Введение (начало):**  
«На сегодняшний день [сфера] становится всё более востребованным направлением для [цель]. В связи с этим [организации/пользователи] стремятся [действие]. [Термин] – это [определение], позволяющее [функции]. В данной курсовой работе необходимо разработать [WEB-ресурс / веб-сервис] с целью [цель].»

**Ссылка на рисунок:**  
«На рисунке N представлена [что]. [1 предложение пояснения].»  
Подпись: `Рисунок N – [Название]`

**Ссылка на таблицу:**  
«В качестве [чего] использовалось [что], представленное в таблице N.»  
Подпись: `Таблица N – [Название]`

**Итог разработки:**  
«В результате выполнения поставленной задачи было разработано программное решение, которое является WEB-ресурсом «[Название]». Данное решение является клиент-серверным, реализовано разграничение полномочий по ролям.»

**Заключение (фрагмент):**  
«На этапе тестирования было выполнено тестирование функциональных возможностей программного решения, найдены и исправлены недочёты, связанные с функциональностью и защитой. Результат выполнения курсового проекта соответствует поставленным задачам.»

## 14. Контрольный чек-лист перед сдачей текста

- [ ] Нет местоимения «мы» / «я» в основном тексте  
- [ ] Есть «На сегодняшний день» и «В связи с этим» во введении  
- [ ] Сквозные термины: WEB-ресурс, веб-сервис, информационная система, реляционная БД  
- [ ] Каждый рисунок упомянут в тексте формулой «На рисунке N…»  
- [ ] Подписи рисунков: **тире**; таблицы — единый стиль (тире или точка)  
- [ ] Роли оформлены шаблоном «Пользователь с ролью «…» обладает…»  
- [ ] Списки функций — «•» и «;» (последний без «;»)  
- [ ] Нет AI-штампов из раздела 11  
- [ ] Предложения не короче 12–15 слов подряд (избегать «телеграфного» стиля)  
- [ ] Стиль ближе к образцу `Пример_ПЗ.txt`, а не к научной статье
